## 3. Ambiguities resolved by default 🟡

- **A1 — Topic status mixes shared and per-user state** (C5 vs §I "progress per user"). Split it in two: `topics.content_status` (not started / materials available / generation pending / lesson available) and `topic_progress.status` per user (not started / studied / revision required / completed).
- **A2 — Hierarchy.** C2 says units → chapters → topics → subtopics, while C3 and §6.3 say units → topics. Default: `units → topics`, with a nullable `topics.parent_topic_id` for subtopics. "Chapter" folds into unit. Lessons are generated per top-level topic, and subtopics become sections of that lesson.
- **A3 — Lesson ownership.** Single-user for now (D5): one lesson per (topic, depth), each with immutable versions (F7). Generating again adds a version; on-demand enrichment adds a version with one extra section (F1 mode 2). The owner/visibility/publish/fork parts of this default return with multi-user (D5, D17).
- **A5 — Workspace `visibility`** (B1) has no defined values and public sharing is out of scope. The column is stored but the only accepted value is `private`.
- **A7 — "Personal notes"** are listed as personal data (§4.3) but have no API or UI requirements. Deferred. All uploaded documents are workspace-shared.
- **A8 — Document ↔ course/topic.** D2 says "assign to courses" (plural), but D5 gives each chunk a single `course_id`. Default: a document belongs to at most one course, and documents map to topics many-to-many (`document_topics`) by hand. No per-chunk LLM topic classification in MVP (cost). Retrieval scope is the course's documents plus workspace documents that have no course.
- **A9 — Document kind.** Question extraction (H3) needs to know when a file is a question paper. The user picks a `kind` at upload: `syllabus | textbook | notes | question_paper | other`.
- **A10 — Syllabus re-parse.** Each course has one active syllabus. Parse output is a *draft* that the user reviews and confirms (which triggers Q3). A re-parse creates a new draft and never silently overwrites a confirmed structure.
- **A11 — Permission matrix.** The PRD role lists overlap ("manage most workspace resources"). Default matrix:

  | Action | Owner | Admin | Editor | Viewer |
  |---|:-:|:-:|:-:|:-:|
  | Delete workspace | ✓ | | | |
  | Edit workspace name/description | ✓ | ✓ | | |
  | Invite / remove / change role of Editor, Viewer | ✓ | ✓ | | |
  | Invite / remove / change role of Admin | ✓ | | | |
  | Create / edit / delete courses, edit + confirm syllabus | ✓ | ✓ | | |
  | Upload documents | ✓ | ✓ | ✓ | |
  | Delete / reprocess documents | ✓ | ✓ | own uploads | |
  | Publish lessons, regenerate shared lessons, edit question bank | ✓ | ✓ | ✓ | |
  | View shared content, private lessons, tutor, quizzes, own progress | ✓ | ✓ | ✓ | ✓ |
  | Read another user's private data | ✗ | ✗ | ✗ | ✗ |

  A workspace has exactly one owner. Ownership transfer is out of MVP.
- **A12 — Invitations.** An email invite is bound to that address: the accepting account must have the same verified email. A link invite works for any signed-in user and carries a role, an expiry, a max-uses count and a revoke flag. The role is fixed at invite time and can never be Owner.
- **A13 — Removed members / deleted workspaces.** A removed member's private data in that workspace (sessions, progress) is kept but inaccessible, and comes back if they are re-invited. Deleting a workspace deletes everything in it, including members' private data. The owner gets a warning first. Users can delete their own private data at any time.
- **A14 — Progress states are undefined** (C5, H6, §I). Defaults: *Studied* = the user clicked "Mark studied". *Completed* = studied and latest topic quiz ≥ 70%. *Revision required* = latest quiz < 50%, or studied more than 14 days ago with no activity since. *Revision due* (analytics) = topics in Revision required. Thresholds are constants in one module.
- **A15 — Language.** Lessons are generated in English, and Postgres full-text search uses the `english` config. The tutor answers in the user's preferred language (prompt instruction only).
- **A16 — Exam answer length** (G1 Exam mode). Default word targets: 2-mark ≈ 60, 5-mark ≈ 250, 10-mark ≈ 600. They live in the prompt template and are versioned with it.
- **A17 — Image block** (F5). An LLM can't produce images, and external image URLs are untrusted (tracking, injection). Image blocks may only reference assets extracted from uploaded documents, served through signed URLs.
- **A18 — Usage limits** (§12.6) have no values. Each workspace gets a monthly token and search-call budget set from env. Exceeding it hard-stops with a clear error. Real values get set after measuring costs in Phase 4.
- **A19 — Email.** Verification, password reset and invitations all need an email sender, which isn't in the stack. Default: SMTP settings, with Mailpit in docker-compose for development. The production provider is TBD (any SMTP). Login isn't blocked on verification, but accepting an email invite requires a verified email.
- **A20 — "Evidence sufficiency"** (§1.1 step 4, E1) is undefined. Phase 3: judged by the research planning call, which is needed anyway to write focused queries. It returns `covered`, `missing` and `sufficient` from the student's top passages (syllabus documents excluded: a syllabus lists what to learn, it doesn't teach it). No separate heuristic. Phase 4 calls research only when `sufficient` is false, or when the student asks for it (E1).
- **A21 — Course/unit quizzes** (H4) have no endpoint; §7 only has `POST /topics/{id}/quizzes`. Add `POST /courses/{id}/quizzes` with an optional `unit_id` / `topic_ids` scope. Quizzes are private to whoever creates them. The shared asset is the question bank.

## 4. Missing implementation details (filled in)

- **M1 — Entities missing from §6.3:** `refresh_tokens` (rotation + reuse detection), `invitations`, `email_tokens` (verify/reset), `document_topics`, `lesson_feedback`, `quiz_attempt_answers`, `document_assets` (extracted images). Each one ships with a migration.
- **M2 — Endpoints the functional requirements need but §7 omits:** verify-email, forgot/reset-password, list/revoke/accept invitations, `PATCH` member role, `GET /workspaces/{id}/courses`, `DELETE /courses/{id}`, unit/topic CRUD + reorder (C4), syllabus confirm, document↔topic mapping, signed document URL (D7 citation navigation), lesson enrich (F1 mode 2), `DELETE` tutor session (G2), question-bank list/review/edit (H3), course quizzes (A21), mark-studied. All go under `/api/v1` with the same conventions.
- **M4 — Reranker** isn't specified. Evaluated in Phase 2 and not shipped: see D9.
- **M6 — Diagram/formula validation** (F6, §11.5). Python can't parse Mermaid or KaTeX, so the worker image includes Node and a small script (`mermaid.parse` under jsdom, `katex.renderToString`). As a second safety net, the frontend reports render failures, which flags the lesson.
- **M7 — Job events** (§7 SSE). Workers write `job_events` rows. The SSE endpoint tails the table (polling about once a second) and supports `Last-Event-ID` replay. Redis pub/sub only gets added if polling load becomes a problem.
- **M8 — SSE auth.** `EventSource` can't send an `Authorization` header, and the tutor endpoint is a `POST`. **Superseded by D25:** sign-in uses HttpOnly cookies, so job-progress streams keep using `EventSource`; the tutor uses `fetch()` streaming because it's a POST.
- **M9 — Citation contract** (rule 16). The LLM receives evidence labelled `[S1]…[Sn]` and may cite labels only. The backend maps labels to chunk or research-source IDs and rejects unknown labels. `lesson_citations` keeps a snapshot of the quoted text, so a citation survives deletion of its document and is shown as "source removed".
- **M10 — Upload limits** aren't specified. Default: 100 MB per file (configurable). The type comes from content sniffing, not the file extension.
- **M11 — Database access style.** SQLAlchemy 2 **sync** sessions (psycopg 3) in both the API and the Celery workers, so there's one repository layer instead of duplicated async and sync versions. Async is used only for streaming LLM responses.
- **M12 — Token counting** for chunk sizes: ~4 characters per token (`app/core/tokens.py`). `tiktoken` was planned, but it downloads its vocabulary at runtime and Gemini tokenizes differently anyway. Swap in a real tokenizer only if chunk sizes measurably miss.
- **M13 — Tests.** A deterministic fake LLM provider lives in tests only (never as product fallback, per rule 24). Tests run against real Postgres + pgvector from docker-compose, not SQLite.
- **M14 — Benchmark data** (§16) needs real course material from you: 1 syllabus, 1–2 textbook chapters, 1–2 previous-year papers, all for the same course. **Status:** syllabus received (`test_material/AIML-R23.pdf`, 215 pages, the whole programme). The 28-question retrieval benchmark is `backend/tests/benchmark/aiml_r23.json`; it was drafted by Claude and needs a human review pass. Textbook chapters and previous-year papers are still missing: retrieval on textbook-style prose is unmeasured. **Question papers (2026-11-06):** you had none ("build on your own please"), so `backend/tests/benchmark/synthetic_os_paper.py` is a **synthetic** Operating System (AM401) paper written by Claude in the common B.Tech format, with an answer key for every question (marked SYNTHETIC on every page and in the file name). It's clean digital text, so it says nothing about scanned papers or unusual layouts. Replace or add real papers when you have them.
- **M15 — Claim verification (E2 step 10).** One LLM call lists up to 8 claims, citing source labels (S1… web, M1… student material). Labels that don't resolve are dropped, and so are claims with no resolvable support (rule 16). **Verified** means supported by ≥ 2 independent domains, or by one authoritative source (quality ≥ 0.75: academic, official docs, encyclopedia), or by the student's own material. **Disputed** means any source contradicts it. Otherwise **unverified**. A source is verified if it supports a verified claim, and disputed if it contradicts any claim.
- **M16 — Source quality (E3)** is a deterministic domain tier (`modules/research/quality.py`), so scores are explainable and free. Anyone-can-upload sites (academia.edu, slideshare, studocu…) rank below universities even on `.edu`. Passages are picked by topic-term overlap. A window needs real sentences, so menus and link lists never become evidence.
- **M17 — Stalled jobs.** A job that's queued or running but has reported no progress for 15 minutes counts as dead (worker killed, message lost). Reprocess, re-parse and research then start a new job instead of answering "already running" forever. Every stage emits progress events well inside that window.
- **M18 — Lesson evidence and citations (M9 applied).** Evidence order: pinned documents (D12), passages mapped to the topic, then retrieval, with syllabi excluded. That's at most 10 material passages (M1…) and 6 web sources (W1…) from the topic's research, reused if under 7 days old, otherwise run inline and stopped after the gap check if materials suffice (E1). Only labels that resolve are kept, and "[M1]"-style labels left in prose are moved into the block's citations. Each cited label becomes a `lesson_citations` row with a quote snapshot. Enriched versions continue the numbering, so labels never collide. A block with no citations is labelled "AI-written explanation" in the UI (§11.2).

- **M19 — Tutor answers (Module G).** One streamed fast-tier call per answer. Evidence: up to 6 passages from hybrid retrieval over the course (syllabus included: "what's in unit 3?" is a fair question), the topic's research if under 7 days old (up to 4 sources), and, only when the student ticks "also search the web", one Tavily search filtered like research (URL safety, dedupe, quality tier; counted in the budget, not stored). The retrieval query adds the topic title and the previous question, so follow-ups like "and the second one?" still find passages. The lesson outline is context, not evidence. The last 10 messages are sent as history. Citations: `[M1]`/`[W1]` markers in the text; unknown labels are removed and each used one is saved with a quote. Follow-up questions come after a `[[FOLLOW-UPS]]` marker, held back from the stream. The question is saved before the stream opens (budget errors are plain 429s). The answer is saved however the stream ends: complete, error (partial text kept) or interrupted (client disconnected).
- **M20 — Question extraction (H3).** Runs on its own after a `question_paper` document with a course is indexed, or on request for any course document. One LLM call per ~12k characters. Questions are cleaned (type, marks, options), de-duplicated, given their page, and mapped to a top-level topic by embedding. They're saved as drafts. Re-extracting replaces drafts that haven't been approved and never duplicates approved ones. A topic quiz uses approved questions only.
- **M21 — Quizzes and marking (H4, H5).** A quiz takes a random sample of matching approved questions first. One LLM call writes answer keys for sampled questions that lack them (extracted papers have none) plus the new questions needed; it sees the sampled questions so it doesn't reword them. Invalid keys or questions are dropped, and a rubric that doesn't add up to the marks becomes the PRD's split (accuracy 40%, then explanation, example, presentation). MCQ, true/false, numerical (within 1%) and fill-in (accepted alternatives, case and punctuation ignored) are marked deterministically at submit. Written answers get one rubric-anchored call per attempt at temperature 0 (R16): student answers are fenced as untrusted, the rubric is stored with every score, scores are labelled estimates, and blank answers score 0 without a call. A failed marking job can be retried ("Grade again"). Answer keys are never sent before an attempt.
- **M22 — Progress (A14, H6).** Status is derived when read, not stored, because A14's 14-day rule depends on time. Thresholds live in `modules/analytics/service.py`. A question counts as correct at ≥ 60% of its marks. "Studied" counts topics you marked, even when a weak quiz puts them in "Revise". Revise-by is the last activity + 14 days, or now for topics needing revision. Weak = latest quiz < 50%, strong = ≥ 80%.

## 5. Technical risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | Scope: 8 modules, ~30 tables, ~60 endpoints. The risk is going broad and shallow. | Strict phase gates. Nothing gets ticked in `CHECKLIST.md` without meeting the Definition of Done. |
| R2 | Cross-site refresh cookie in production (see Q6). SSE through a Vercel rewrite may buffer or time out. | Closed by Q6: one origin on Vercel in production, and the Vite proxy in development. Vercel stops a function after 300 s (Hobby). Tutor answers finish well within that. The job-progress stream gets cut, and `EventSource` reconnects and resumes from `Last-Event-ID`. |
| R3 | Embedding lock-in: a pgvector column has a fixed dimension, and HNSW supports at most 2000 dims for `vector`. | Fixed at 1536. Each chunk stores its model id. Re-embed job when the model changes. |
| R4 | Filtered HNSW search (`WHERE workspace_id=…`) can return fewer than k results. | Require pgvector ≥ 0.8 with `hnsw.iterative_scan`. Checked 2026-11-06: Neon ships pgvector 0.8.0. |
| R5 | Structured output differs across providers. Gemini, OpenAI strict mode and local endpoints each accept a different JSON-schema subset, and a 15-way block union often fails. | Generate lessons section by section. Use native structured output where it's supported, otherwise JSON mode + Pydantic validation + a bounded repair retry. |
| R6 | PyMuPDF's AGPL obligation (Q2). Heading detection quality on unusual textbook layouts. | Licence is your call: open-source the code or buy a license. Measure heading/chunk quality on the M14 benchmark. |
| R7 | Mermaid validation in Node/jsdom doesn't perfectly match browser rendering. | Client-side failure reporting (M6) as a second net. |
| R8 | Auto batch generation (Q3): 50–150 topics × (sufficiency check + 3–5 searches + 5–10 pages + long generation + retries). | Cost estimate shown at confirm, workspace budget (A18), cheaper model for classification, per-topic research cache, cancellable batches. |
| R9 ✅ | RLS plumbing. The app's DB role must not own the tables (or use `FORCE ROW LEVEL SECURITY`). Every transaction needs `SET LOCAL app.user_id` even with pooled connections. Workers need their own context. Migrations run as the owner role. | Built with multi-user (D27). Finding: the development role `semsaviour` is a **superuser**, and superusers ignore RLS even when forced, so API transactions also `SET LOCAL ROLE semsaviour_rls` (a non-superuser role the migration creates; the migration needs CREATEROLE, or have an admin create the role first). Tested with raw SQL that forgets its WHERE clause (`test_row_level_security`). |
| R10 | Prompt injection through *uploaded documents*, not only web pages. | All evidence is delimited as data, and no tools are driven by evidence. Output is render-only: react-markdown without raw HTML, Mermaid `securityLevel: 'strict'`, KaTeX `trust: false`. |
| R11 ✅ | SSRF in page fetching, including DNS rebinding through redirects. | Removed: no server-side page fetching (D10). Stored and displayed source URLs must still be http(s) on public hosts. That rejects loopback, private, link-local and metadata IPs, IPv4-mapped IPv6, numeric host forms like `127.1` and `0x7f…`, intranet suffixes and credentials (`modules/research/urls.py`, 20 cases tested). |
| R12 | Gemini free-tier data use (Q1). | Paid key before launch. Disclose in the privacy policy. |
| R13 | Local environment: Docker Desktop is installed but its daemon isn't running. There's no local Postgres, Redis or Tesseract, and Celery doesn't support Windows natively. | All infrastructure and workers run through docker-compose. |
| R14 ✅ | MinIO's community distribution changed in 2025. | Confirmed: `minio/minio` no longer pulls from Docker Hub. Development uses `cgr.dev/chainguard/minio` (maintained build, includes `mc` for health checks). Production uses R2/S3 (PRD §13). |
| R15 | Copyright: users share textbooks in workspaces, and lessons quote them. | Product/legal decision for you, not an engineering one. Noted. |
| R16 | LLM grading varies between runs (H5). | Rubric-anchored structured output, temperature 0, store the rubric with each evaluation, label scores "estimated". |
| R17 | Slow network on the dev machine (~1 s TCP connect to Google; a dropped connection on the first call). | One provider client per process (keep-alive), batched requests, transport errors retried with backoff. |
| R18 | Host port 6379 is taken by a Redis inside WSL. | Compose maps Redis to `127.0.0.1:6380`. The worker uses the internal `redis:6379`. |
| R19 | Gemini overload: `gemini-3.8-flash` and `3.7-flash` answered 503 "high demand" or 429 for many minutes at a time, and the first live syllabus parses all failed. | Fast tier is a preference list (D11). Overload or rate limit moves to the next model at once; backoff only after a full pass fails. Live runs were then served by 3.5-flash and 3.1-flash-lite with the same benchmark results. |
| R20 | Containers don't see `.env` edits: `docker compose restart` keeps the old environment (the worker said `TAVILY_API_KEY is not set` after the key was added). | After editing `.env`: `docker compose up -d --force-recreate worker` (README). |
| R21 | Gemini free tier for lessons: pro models have zero quota, and `gemini-3.8-flash` / `3.5-flash` allow **20 requests per day each**. | The smart tier falls back to flash-lite. A model that replies "retry in hours" is skipped for that long (per-process cooldown) instead of being asked on every call. Live: a flash lesson on Deadlocks had 13 sections and ~3,300 words with 34 of 35 blocks cited; flash-lite lessons are thinner. A paid key is recommended before relying on batches. |
| R22 | Lesson generation takes ~30 s to 3 min, and the worker runs 2 jobs at a time, so a 50-topic batch takes a while and holds both slots. | Cancellable batch, progress on the course page. If uploads ever queue behind lessons, split the generation queue onto its own worker (PRD §10.2). |
| R24 | Topic mapping of questions: on-course and off-course similarity scores nearly touch. | Measured on the synthetic OS paper: on-course questions scored 0.594–0.750 (all 31 top-1 topics correct), off-course ones (DBMS, ML, C, TOC) 0.513–0.588. The existing 0.6 threshold maps 30 of 31 and rejects all 6 off-course; 0.55 would have mapped BCNF and ACID questions into Operating Systems. Kept 0.6 (D22). Unmapped drafts are fixed in review. |
| R25 | The synthetic paper was written by the same model family that extracts it, from clean text. | Extraction scored 31/31 on it with flash-lite, which is an upper bound. Real scanned papers (OCR, two columns, handwriting) are untested until you have some (M14). |
| R23 ✅ | Uncommitted writes held across slow external calls (LLM, embeddings) kept row locks: deleting a workspace waited for a lesson's LLM call to return. | Found in E2E and fixed: commit before every external call (lesson repair path; ingestion's topic mapping now runs after the indexing commit). |
